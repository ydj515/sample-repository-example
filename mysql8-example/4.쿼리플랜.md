## 1. 쿼리 실행 계획이란?

쿼리 실행 계획(Query Plan)은 우리가 작성한 SQL 쿼리를 데이터베이스 옵티마이저가 **어떤 방식과 순서로 실행할지 결정한 상세한 절차**입니다. 마치 내비게이션이 목적지까지 가는 여러 경로 중 가장 효율적인 경로를 찾아주는 것과 같습니다.

`EXPLAIN`은 이 계획을 우리에게 보여주는 명령어로, 다음과 같은 질문에 답을 줍니다.
* 쿼리가 인덱스를 잘 사용하고 있는가?
* 불필요하게 테이블 전체를 읽고 있지는 않은가? (Full Table Scan)
* 테이블 조인(JOIN) 순서는 효율적인가?
* 정렬(ORDER BY)이나 그룹화(GROUP BY) 시 불필요한 부하가 발생하지는 않는가?

---

## 2. `EXPLAIN` 명령어 사용법

사용법은 간단합니다. 분석하고 싶은 `SELECT` 쿼리 앞에 `EXPLAIN` 키워드만 붙여주면 됩니다.

```sql
EXPLAIN SELECT * FROM users WHERE status = 'ACTIVE' ORDER BY created_at DESC;
```

## 3\. `EXPLAIN` 결과의 핵심 컬럼 해부

`EXPLAIN` 결과에서 이 네 가지 컬럼만 제대로 읽을 수 있어도 쿼리 성능의 80% 이상을 파악할 수 있습니다. **좋은 쿼리는 `type`이 빠르고, `key`가 존재하며, `rows`가 적고, `Extra`에 나쁜 신호가 없는 쿼리**입니다.

### 3.1. `type` (접근 방식)

**가장 중요한 컬럼**으로, MySQL이 테이블의 행에 어떻게 접근하는지를 보여줍니다. 아래로 갈수록 성능이 나빠지므로, **최대한 위쪽에 위치시키는 것이 쿼리 튜닝의 핵심 목표**입니다.

  * **`system`**: 테이블에 행이 1개뿐인 경우. (가장 빠름)
  * **`const`**: **Primary Key**나 **Unique Key** 조건으로 검색하여 결과가 **반드시 1개**일 때. `SELECT ... WHERE id = 5;` 처럼 고유한 값을 찾는 경우입니다. (매우 빠름)
  * **`eq_ref`**: 조인(JOIN) 시 연결되는 테이블이 **Primary Key**나 **Unique Key**를 통해 **항상 1개의 행만**을 가지는 경우.
  * **`ref`**: `const`와 비슷하지만, 검색 결과가 **여러 개일 수 있는 경우**입니다. 고유하지 않은 인덱스(Non-unique index)를 사용할 때 나타납니다. (빠름)
  * **`range`**: 특정 **범위**를 검색할 때 인덱스를 사용합니다. `WHERE id BETWEEN 10 AND 20;` 또는 `WHERE status IN ('A', 'B');` 와 같은 쿼리에서 나타납니다. (괜찮음)
  * **`index`**: 인덱스 전체를 스캔합니다. 테이블 전체를 스캔하는 `ALL`보다는 빠르지만 (인덱스가 테이블 데이터보다 작으므로), 여전히 모든 인덱스를 읽어야 하므로 좋은 방식은 아닙니다.
  * **`ALL`**: **테이블 전체를 스캔(Full Table Scan)** 하는 최악의 경우입니다. 인덱스를 전혀 사용하지 못하고 처음부터 끝까지 모든 행을 읽어서 조건을 확인합니다. 데이터가 많은 테이블에서 `ALL`이 나타나면 반드시 개선해야 합니다. (매우 느림)

### 3.2. `key` (실제 사용된 인덱스)

MySQL 옵티마이저가 쿼리를 실행하기 위해 **실제로 선택한 인덱스의 이름**을 보여줍니다.

  * 이 컬럼이 **`NULL`** 이라면, MySQL이 **인덱스를 사용하지 못했다**는 강력한 신호입니다. `WHERE` 조건절의 컬럼에 인덱스가 없는지, 또는 인덱스를 사용하지 못하는 형태로 쿼리를 작성했는지 확인해야 합니다.
  * 참고로 `possible_keys`라는 컬럼은 옵티마이저가 "사용할 수 있겠다"고 **고려했던 인덱스들의 목록**이고, `key`는 그중에서 **최종적으로 선택된 것**입니다.

### 3.3. `rows` (조회 예상 행 수)

쿼리를 처리하기 위해 MySQL이 **읽어야 할 것으로 예측하는 행의 수**입니다.

  * 이 값은 통계 정보에 기반한 **추정치**이므로 100% 정확하지는 않습니다.
  * 하지만 이 숫자가 **비정상적으로 크다면** 쿼리가 비효율적일 가능성이 높다는 것을 의미합니다. `type`이 `ALL`일 경우, 이 값은 테이블의 전체 행 수와 비슷하게 나옵니다.
  * 우리의 목표는 `type`과 `key`를 개선하여 이 `rows` 값을 최대한 줄이는 것입니다.

### 3.4. `Extra` (추가 정보)

쿼리 실행에 대한 **중요하고 부가적인 정보**를 담고 있으며, 성능에 대한 결정적인 힌트를 제공합니다.

#### 긍정적인 신호 👍

  * **`Using index`**: "커버링 인덱스(Covering Index)"가 사용되었음을 의미합니다. 쿼리에 필요한 모든 데이터가 인덱스에 포함되어 있어, 굳이 테이블 데이터를 읽을 필요 없이 **인덱스만으로 처리가 완료**되는 가장 이상적인 상태 중 하나입니다.

#### 부정적인 신호 👎

  * **`Using filesort`**: MySQL이 정렬을 위해 인덱스를 사용하지 못하고, 별도의 정렬 작업을 수행해야 함을 의미합니다. `ORDER BY` 구문에서 사용한 컬럼에 인덱스가 없거나, 다른 조건과 섞여 인덱스를 탈 수 없을 때 발생합니다. 대용량 데이터 정렬 시 매우 느려질 수 있습니다.
  * **`Using temporary`**: 쿼리 결과를 처리하기 위해 MySQL이 **임시 테이블**을 생성했음을 의미합니다. 주로 `GROUP BY`와 `ORDER BY`의 컬럼이 다르거나, `UNION`을 사용할 때 발생합니다. 디스크에 임시 테이블이 생성될 경우 심각한 성능 저하를 유발합니다.

## 4\. 성능 개선을 위한 실전 팁 (요약)

  * **`WHERE`절의 컬럼을 가공하지 마세요**: `WHERE YEAR(created_at) = 2025` 대신 `WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'` 와 같이 작성해야 인덱스를 사용할 수 있습니다.
  * **다중 컬럼 인덱스의 순서를 고려하세요**: `INDEX(a, b)`는 `WHERE a = ?` 또는 `WHERE a = ? AND b = ?` 에는 효과적이지만, `WHERE b = ?` 에는 효과가 없습니다.
  * **`ORDER BY`와 `GROUP BY`에 인덱스를 활용하세요**: 정렬과 그룹화에 사용되는 컬럼에도 인덱스를 생성하면 `Using filesort`, `Using temporary`를 피할 수 있습니다.
  * **커버링 인덱스를 적극적으로 사용하세요**: `SELECT *` 보다는 쿼리에 필요한 컬럼만 명시하고, 해당 컬럼들을 인덱스에 포함시켜 `Using index`를 유도하세요.

## 5\. 성능 개선을 위한 실전 팁: Before & After

`EXPLAIN`을 통해 문제점을 파악했다면, 이제 쿼리를 어떻게 수정해야 할까요? 가장 흔히 발생하는 비효율적인 쿼리 패턴과 해결책을 소개합니다.

### 예제 1: 인덱스 컬럼 가공 (함수 사용)

가장 흔하게 저지르는 실수 중 하나입니다. **`WHERE` 절에서 인덱스가 걸린 컬럼을 함수로 감싸거나 연산을 하면** 옵티마이저가 인덱스를 사용하지 못합니다.

  * **상황**: `accounts` 테이블의 `created_at` 컬럼에는 인덱스가 걸려있습니다.

#### worst (Before)

```sql
EXPLAIN SELECT * FROM accounts WHERE YEAR(created_at) = 2025;
```

  * **`EXPLAIN` 결과 (예상)**
    | id | type | possible_keys | key  | rows   | Extra       |
    |:---|:-----|:--------------|:-----|:-------|:------------|
    | 1  | ALL  | NULL          | NULL | 500000 | Using where |
  * **문제점**: `YEAR()` 함수 때문에 `created_at`의 인덱스를 전혀 사용하지 못하고, `type`이 **`ALL`**(테이블 전체 스캔)이 되었습니다. 50만 건의 데이터를 모두 읽어야 하므로 매우 비효율적입니다.

#### well (After)

컬럼 자체는 그대로 두고, 비교하는 값을 가공하여 범위(Range)로 검색하도록 변경합니다.

```sql
EXPLAIN SELECT * FROM accounts
WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01';
```

  * **`EXPLAIN` 결과 (개선)**
    | id | type  | possible\_keys   | key              | rows  | Extra                 |
    |:---|:------|:-----------------|:-----------------|:------|:----------------------|
    | 1  | range | idx\_created\_at | idx\_created\_at | 45000 | Using index condition |
  * **개선점**: `type`이 `range`로 바뀌면서 `idx_created_at` 인덱스를 효과적으로 사용하게 되었습니다. 예상 조회 행(`rows`)도 50만 건에서 4.5만 건으로 크게 줄었습니다.

### 예제 2: `ORDER BY`로 인한 `filesort` 발생

`WHERE` 절은 인덱스를 잘 사용했지만, `ORDER BY` 절의 컬럼이 인덱스와 맞지 않아 불필요한 정렬 작업이 발생하는 경우입니다.

  * **상황**: `users` 테이블에는 `status` 컬럼에만 단일 인덱스(`idx_status`)가 있습니다.

#### worst (Before)

```sql
EXPLAIN SELECT id, name FROM users
WHERE status = 'ACTIVE' ORDER BY last_login_at DESC;
```

  * **`EXPLAIN` 결과 (예상)**
    | id | type | key        | rows  | Extra                           |
    |:---|:-----|:-----------|:------|:--------------------------------|
    | 1  | ref  | idx_status | 80000 | Using where; **Using filesort** |
  * **문제점**: `status` 조건은 `idx_status` 인덱스를 잘 사용했지만(`type: ref`), 정렬 기준인 `last_login_at`은 인덱스에 없어 `Using filesort`가 발생했습니다. 8만 건의 데이터를 메모리나 디스크에서 정렬해야 하므로 부하가 큽니다.

#### well (After)

이런 경우, 쿼리 조건과 정렬 조건을 모두 만족하는 다중 컬럼 인덱스(Composite Index)를 생성하는 것이 해결책입니다.

```sql
-- 해결책: status와 last_login_at을 묶어 인덱스 생성
CREATE INDEX idx_status_last_login ON users (status, last_login_at);

-- 인덱스 생성 후 다시 쿼리 실행
EXPLAIN SELECT id, name FROM users
WHERE status = 'ACTIVE' ORDER BY last_login_at DESC;
```

  * **`EXPLAIN` 결과 (개선)**
    | id | type | key                      | rows  | Extra       |
    |:---|:-----|:-------------------------|:------|:------------|
    | 1  | ref  | idx\_status\_last\_login | 80000 | Using where |
  * **개선점**: `Using filesort`가 사라졌습니다. 새로 만든 `idx_status_last_login` 인덱스는 이미 `status`와 `last_login_at` 순서로 정렬되어 있어, 별도의 정렬 작업 없이 인덱스를 순서대로 읽기만 하면 되기 때문입니다.
