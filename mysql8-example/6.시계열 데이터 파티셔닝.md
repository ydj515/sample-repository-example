## MySQL 시계열 데이터 파티셔닝: 고려사항

파티셔닝을 성공적으로 적용하기 위해선 다음 7가지 요소를 신중하게 고려해야 합니다.

### **1. 파티셔닝 키 (Partitioning Key) 선정**

가장 중요한 결정입니다. 시계열 데이터에서는 대부분 **시간 관련 컬럼**(`DATE`, `DATETIME`, `TIMESTAMP`)을 파티셔닝 키로 사용합니다.

  * **쿼리 패턴:** `WHERE` 절에 파티셔닝 키가 자주 사용되어야 \*\*파티션 프루닝(Partition Pruning)\*\*이 동작하여 성능 향상 효과를 볼 수 있습니다. 예를 들어, `WHERE trade_date BETWEEN '2025-09-01' AND '2025-09-22'` 와 같은 쿼리가 주를 이뤄야 합니다.
  * **데이터 타입:** `DATE`, `DATETIME` 같은 날짜 타입 자체를 사용할 수도 있지만, `YYYYMM` 형식의 `INT` 타입을 사용하는 것도 매우 효율적입니다. `RANGE` 파티션에서 비교 연산이 더 빠르고 명확하기 때문입니다. (제공해주신 `sp_manage_partitions` 프로시저에서 `YEAR(NOW()) * 100 + MONTH(NOW())`를 사용하신 것은 아주 좋은 접근 방식입니다.)

### **2. 파티셔닝 유형 (Partitioning Type) 선택**

MySQL은 여러 파티셔닝 유형을 제공하지만, 시계열 데이터에는 **`RANGE` 파티셔닝**이 거의 항상 정답입니다.

  * **RANGE:** 지정된 범위를 기준으로 데이터를 분리합니다. '2025년 9월 데이터', '2025년 10월 데이터'와 같이 연속적인 데이터를 분리하는 데 최적화되어 있습니다.
  * **LIST:** 특정 값 목록을 기준으로 분리합니다. (예: `country IN ('KR', 'US', 'JP')`) 시계열 데이터에는 적합하지 않습니다.
  * **HASH/KEY:** 데이터를 균등하게 분산시키는 데 목적이 있어, 특정 기간의 데이터를 조회하거나 삭제하는 시계열 데이터의 주요 목적과는 맞지 않습니다.

### **3. 파티션 단위 (Granularity) 결정**

파티션을 얼마나 잘게 나눌지 결정해야 합니다.

  * **고려 요소:**
      * **데이터 발생량:** 하루에 수억 건씩 쌓인다면 일별(Daily) 파티션이 적합할 수 있습니다.
      * **쿼리 범위:** 주로 주 단위로 데이터를 조회한다면 주별(Weekly) 또는 월별(Monthly) 파티션이 효율적입니다.
      * **데이터 보관 주기:** 오래된 데이터를 삭제할 때 월 단위 삭제가 편하다면 월별 파티션을 선택합니다.
  * **일반적인 선택:** **월별(Monthly)** 또는 **연도별(Yearly)** 파티션이 관리 부담과 성능 사이의 균형을 맞추기 좋아 가장 널리 사용됩니다. 제공해주신 예제처럼 월별로 관리하는 것은 훌륭한 시작점입니다.

### **4. Primary Key와 Unique Index 제약**

매우 중요한 제약사항입니다. 파티셔닝을 사용하려면 **파티셔닝 키로 사용하는 컬럼이 Primary Key 또는 모든 Unique Index에 포함되어야 합니다.**

  * 예시: `trade_date`로 파티셔닝을 한다면, PK는 `(trade_id, trade_date)`처럼 구성되어야 합니다. 제공해주신 `stock_trades` 테이블의 `PRIMARY KEY (trade_id, trade_date)`는 이 제약사항을 정확히 만족시키는 올바른 설계입니다.

### **5. 파티션 자동 관리 계획**

파티션은 '일회성 설정'이 아니라 '지속적인 관리'가 필요합니다.

  * **미래 파티션 생성:** 새로운 데이터가 쌓일 파티션을 미리 만들어두어야 합니다. 그렇지 않으면 `MAXVALUE` 파티션에 모든 데이터가 쌓여 파티셔닝의 의미가 퇴색됩니다.
  * **과거 파티션 삭제:** 보관 주기가 지난 데이터는 `DELETE` 쿼리가 아닌 `DROP PARTITION`으로 삭제해야 합니다. 이는 서버에 거의 부하를 주지 않고 즉시 대용량 데이터를 삭제할 수 있는 파티셔닝의 가장 큰 장점 중 하나입니다.
  * **자동화:** 이 두 가지 작업을 **MySQL Event Scheduler**와 **Stored Procedure**를 조합하여 자동화하는 것이 필수적입니다. (제공해주신 `sp_manage_partitions`와 `ev_monthly_partition_maintenance` 이벤트는 미래 파티션 생성 자동화의 정석적인 예시입니다.)

### **6. `MAXVALUE` 파티션의 활용**

`RANGE` 파티셔닝 시 `VALUES LESS THAN (MAXVALUE)`로 정의된 파티션은 예상 범위를 벗어난 모든 데이터를 저장하는 '안전망' 역할을 합니다.

  * 파티션 자동 생성이 실패했을 때 데이터가 누락되는 것을 방지합니다.
  * 주기적으로 `MAXVALUE` 파티션에 데이터가 있는지 모니터링하여 파티션 관리 스크립트가 잘 동작하는지 확인하는 것이 좋습니다.

### **7. 기존 데이터 마이그레이션**

이미 데이터가 존재하는 거대한 테이블에 파티셔닝을 적용하려면 서비스 중단 시간을 최소화하는 전략이 필요합니다.

1.  파티션이 적용된 새로운 임시 테이블을 생성합니다.
2.  기존 테이블의 데이터를 임시 테이블로 이전합니다. (`INSERT INTO ... SELECT ...`)
3.  `RENAME TABLE`을 이용해 기존 테이블과 임시 테이블의 이름을 원자적으로(atomically) 변경합니다.
4.  대용량 테이블의 경우 `pt-online-schema-change`와 같은 툴을 사용하는 것을 고려해야 합니다.

### MySQL 시계열 데이터 파티셔닝 진행 방법 (예제 기반)

제공해주신 코드를 바탕으로, 신규/기존 테이블에 파티셔닝을 적용하고 관리하는 전체적인 흐름을 보여드리겠습니다.

### **1단계: 파티션 테이블 생성**

월별 파티션을 적용한 `stock_trades` 테이블의 DDL 예시입니다. 초기 1년 치와 미래를 위한 `p_future` 파티션을 생성합니다.

```sql
CREATE TABLE stock_trades (
    trade_id BIGINT NOT NULL AUTO_INCREMENT,
    trade_date DATE NOT NULL,
    -- ... 다른 컬럼들 ...
    PRIMARY KEY (trade_id, trade_date)
)
PARTITION BY RANGE ( YEAR(trade_date) * 100 + MONTH(trade_date) ) (
    PARTITION p202501 VALUES LESS THAN (202502),
    PARTITION p202502 VALUES LESS THAN (202503),
    PARTITION p202503 VALUES LESS THAN (202504),
    PARTITION p202504 VALUES LESS THAN (202505),
    PARTITION p202505 VALUES LESS THAN (202506),
    PARTITION p202506 VALUES LESS THAN (202507),
    PARTITION p202507 VALUES LESS THAN (202508),
    PARTITION p202508 VALUES LESS THAN (202509),
    PARTITION p202509 VALUES LESS THAN (202510),
    PARTITION p202510 VALUES LESS THAN (202511),
    PARTITION p202511 VALUES LESS THAN (202512),
    PARTITION p202512 VALUES LESS THAN (202601),
    PARTITION p_future VALUES LESS THAN (MAXVALUE)
);
```

### **2단계: 파티션 관리 프로시저 생성 (신규 생성 및 과거 삭제)**

제공해주신 프로시저를 조금 더 개선하고, **오래된 파티션을 삭제하는 프로시저**를 추가하는 것이 중요합니다.

**A. 신규 파티션 생성 프로시저**

```sql
-- 다음 달 파티션을 생성하는 프로시저
DELIMITER //
CREATE PROCEDURE sp_add_partition_monthly()
BEGIN
    -- 2달 뒤의 파티션을 미리 생성합니다. (예: 9월에 11월 파티션 생성)
    DECLARE dt_target DATE DEFAULT DATE_ADD(NOW(), INTERVAL 2 MONTH);
    DECLARE partition_key INT;
    DECLARE partition_name VARCHAR(20);
    DECLARE partition_exists INT DEFAULT 0;

    SET partition_key = YEAR(dt_target) * 100 + MONTH(dt_target);
    SET partition_name = CONCAT('p', partition_key);

    -- 파티션 존재 여부 확인
    SELECT COUNT(1) INTO partition_exists
    FROM information_schema.partitions
    WHERE table_schema = DATABASE()
      AND table_name = 'stock_trades'
      AND partition_name = partition_name;

    -- 파티션이 없을 때만 생성
    IF partition_exists = 0 THEN
        -- p_future 파티션을 리빌딩하여 새로운 파티션을 추가하고, p_future는 MAXVALUE로 유지
        SET @sql = CONCAT(
            'ALTER TABLE stock_trades REORGANIZE PARTITION p_future INTO (',
            'PARTITION ', partition_name, ' VALUES LESS THAN (', partition_key + 1, '),',
            'PARTITION p_future VALUES LESS THAN (MAXVALUE)',
            ')'
        );
        PREPARE stmt FROM @sql;
        EXECUTE stmt;
        DEALLOCATE PREPARE stmt;
    END IF;
END //
DELIMITER ;
```

**B. 오래된 파티션 삭제 프로시저**

```sql
-- 13개월 이전의 오래된 파티션을 삭제하는 프로시저
DELIMITER //
CREATE PROCEDURE sp_drop_old_partition_monthly()
BEGIN
    -- 13개월 전의 파티션을 삭제 대상으로 지정
    DECLARE dt_target DATE DEFAULT DATE_SUB(NOW(), INTERVAL 13 MONTH);
    DECLARE partition_key INT;
    DECLARE partition_name VARCHAR(20);
    DECLARE partition_exists INT DEFAULT 0;

    SET partition_key = YEAR(dt_target) * 100 + MONTH(dt_target);
    SET partition_name = CONCAT('p', partition_key);

    -- 삭제할 파티션 존재 여부 확인
    SELECT COUNT(1) INTO partition_exists
    FROM information_schema.partitions
    WHERE table_schema = DATABASE()
      AND table_name = 'stock_trades'
      AND partition_name = partition_name;

    -- 파티션이 존재하면 삭제
    IF partition_exists > 0 THEN
        SET @sql = CONCAT('ALTER TABLE stock_trades DROP PARTITION ', partition_name);
        PREPARE stmt FROM @sql;
        EXECUTE stmt;
        DEALLOCATE PREPARE stmt;
    END IF;
END //
DELIMITER ;
```

### **3단계: MySQL 이벤트 스케줄러 등록**

위에서 만든 두 프로시저를 매월 1일에 자동으로 실행하도록 이벤트를 등록합니다.

```sql
-- MySQL 이벤트 스케줄러 활성화 (서버 설정에서 비활성화된 경우)
SET GLOBAL event_scheduler = ON;

-- 매월 1일 새벽 2시에 파티션 관리 작업을 수행하는 이벤트
CREATE EVENT ev_manage_partitions_monthly
    ON SCHEDULE EVERY 1 MONTH
    STARTS CONCAT(DATE_FORMAT(CURDATE(), '%Y-%m-01'), ' 02:00:00')
    DO
    BEGIN
        CALL sp_add_partition_monthly();
        CALL sp_drop_old_partition_monthly();
    END;
```

## 성능 및 복잡도 분석

### **시간 복잡도 (쿼리 성능)**

  * **파티션 프루닝 적용 시:**
      * `WHERE trade_date = '2025-09-22'` 와 같이 파티션 키로 특정 파티션을 지정할 수 있는 경우, 검색 범위가 전체 테이블 `N`에서 해당 파티션의 데이터 수 `N/P` (P는 파티션 개수)로 줄어듭니다.
      * Big-O 표기법으로는 `O(N)`에서 **`O(N/P)`** 또는 **`O(logP + N/P)`** 로 성능이 향상됩니다. 이는 데이터가 많아질수록 효과가 극대화됩니다.
  * **파티션 프루닝 미적용 시:**
      * `WHERE trade_id = 12345` 와 같이 파티션 키가 `WHERE`절에 없는 경우, MySQL은 어떤 파티션에 데이터가 있는지 알 수 없어 **모든 파티션을 스캔**해야 합니다.
      * 이 경우, 파티션을 열고 닫는 오버헤드로 인해 오히려 비파티션 테이블보다 성능이 저하될 수 있습니다. `O(N)`의 복잡도를 가집니다.

### **공간 복잡도 (데이터 관리)**

  * **총 저장 공간:** 파티셔닝 여부와 관계없이 전체 데이터의 양은 동일하므로 공간 복잡도는 \*\*`O(N)`\*\*으로 같습니다.
  * **관리 효율성:** 파티셔닝의 진가는 데이터 삭제 시에 나타납니다.
      * `DELETE FROM stock_trades WHERE trade_date < '2024-09-01'` : 삭제할 데이터 `K`건에 대해 `O(K)`의 시간이 걸리며, 트랜잭션 로그를 많이 발생시키고 테이블 락을 유발할 수 있습니다.
      * `ALTER TABLE stock_trades DROP PARTITION p202408`: 데이터 양과 무관하게 거의 즉시 완료되는 **`O(1)`** 메타데이터 작업입니다. 서버 부하가 거의 없습니다.


## 4. 심화 주제 (Advanced Topics)

### **4.1. 파티션 테이블과 FOREIGN KEY 제약사항**

파티션 테이블에서 외래 키를 사용하는 것은 매우 까다로우며 일반적으로 **권장되지 않습니다.**

  * **엄격한 제약:** 파티션 테이블 간에 외래 키를 설정하려면, 부모 테이블과 자식 테이블이 **완벽하게 동일한 파티션 구성**을 가져야 합니다. 즉, 파티션 키, 파티션 개수, 각 파티션의 범위 정의가 모두 일치해야 합니다.
  * **현실적인 대안:** 이러한 제약 때문에 대부분의 대용량 시계열 시스템에서는 물리적인 `FOREIGN KEY` 제약 조건을 거는 대신, **애플리케이션 레벨에서 데이터의 정합성을 보장**하는 방식을 택합니다.

### **4.2. `RANGE` vs `RANGE COLUMNS` 파티셔닝**

두 방식의 가장 큰 차이는 파티션 키를 정의하는 방법과 유연성에 있습니다.

  * **`RANGE` 파티셔닝:**

      * **정의:** `PARTITION BY RANGE ( expression )`
      * **특징:** 파티션 키로 \*\*정수 값을 반환하는 표현식(expression)\*\*만 사용할 수 있습니다. `YEAR(trade_date) * 100 + MONTH(trade_date)` 처럼 함수나 계산식을 활용해야 합니다.
      * **장점:** 함수를 사용할 수 있어 복잡한 조건으로 파티션을 나눌 수 있습니다.
      * **단점:** 문법이 다소 복잡하고, 날짜/문자열 타입을 직접 사용하지 못해 변환 과정이 필요합니다.

  * **`RANGE COLUMNS` 파티셔닝:**

      * **정의:** `PARTITION BY RANGE COLUMNS ( column1, column2, ... )`
      * **특징:** 컬럼명을 직접 사용하며, **여러 데이터 타입(`DATE`, `DATETIME`, `VARCHAR` 등)을 지원**합니다.
      * **장점:**
          * 문법이 `PARTITION BY RANGE COLUMNS(trade_date)`처럼 훨씬 직관적이고 간결합니다.
          * 여러 컬럼을 조합하여 파티션 키로 사용할 수 있습니다.
      * **단점:** 파티션 정의에 함수나 표현식을 사용할 수 없습니다.

  * **결론:** 최신 MySQL 버전을 사용하고 `DATE` 또는 `DATETIME` 컬럼 자체로 파티셔닝한다면, 문법이 간결한 **`RANGE COLUMNS`를 사용하는 것이 더 편리하고 권장**됩니다.

### **4.3. 파티션 관리 실패 시 모니터링 및 알림**

파티션 생성/삭제 스크립트가 실패하면 서비스에 큰 영향을 줄 수 있으므로, 다단계 모니터링 시스템 구축이 필수적입니다.

1.  **`MAXVALUE` 파티션 데이터 확인:** 가장 간단하고 효과적인 방법입니다. `p_future` 파티션에 **미래 시점의 데이터가 아닌, 현재나 과거 데이터가 쌓이기 시작했다면** 파티션 생성이 실패했다는 강력한 신호입니다. 주기적으로 아래 쿼리를 실행하여 결과가 없는지 확인합니다.

    ```sql
    SELECT * FROM stock_trades PARTITION (p_future) WHERE trade_date < DATE_ADD(NOW(), INTERVAL 1 MONTH);
    ```

2.  **MySQL 이벤트 스케줄러 상태 확인:** 이벤트 자체가 비활성화되거나 실패할 수 있습니다. `information_schema.events` 테이블을 조회하여 `STATUS`가 `ENABLED`인지, `LAST_EXECUTED` 시간이 정상적인지 확인합니다.

3.  **외부 모니터링 시스템 연동 (권장):**

      * 위 1, 2번 항목을 체크하는 헬스체크(health-check) 스크립트 또는 프로시저를 작성합니다.
      * **Prometheus, Datadog, Zabbix** 같은 외부 모니터링 도구에서 이 스크립트를 주기적으로 호출합니다.
      * 스크립트 결과에 따라 임계치를 설정하고, 문제가 발생하면 **Slack, 이메일, PagerDuty** 등으로 즉시 알림을 받도록 구성합니다.

### **4.4. MySQL 파티션 개수 제한과 성능 영향**

  * **물리적 제한:** MySQL 8.0 기준, 테이블당 가질 수 있는 파티션의 최대 개수는 **8192개**입니다. 이는 서브파티션을 포함한 수치입니다.
  * **성능에 미치는 영향 (중요):** 물리적 제한보다 실질적인 성능 저하가 먼저 발생합니다.
      * **메타데이터 부하 증가:** 각 파티션은 개별 파일처럼 관리되므로, 파티션 수가 수천 개에 달하면 MySQL 서버가 관리해야 할 메타데이터가 늘어나 메모리 사용량이 증가하고 테이블을 여는 속도가 느려질 수 있습니다.
      * **쿼리 옵티마이저 부하:** 파티션 프루닝이 동작하더라도, 쿼리 실행 계획을 세울 때 옵티마이저는 어떤 파티션을 스캔할지 결정해야 합니다. 파티션 수가 과도하게 많으면 이 결정 과정 자체에 미미한 오버헤드가 발생할 수 있습니다. 특히 파티션 프루닝이 불가능한 쿼리는 모든 파티션의 메타데이터를 확인해야 하므로 성능 저하가 더 큽니다.
      * **권장사항:** 특별한 이유가 없다면, 한 테이블의 파티션 개수는 **수백 개 수준으로 유지**하는 것이 안정적입니다. 예를 들어, 10년치 데이터를 일별(daily)로 파티셔닝하면 약 3650개의 파티션이 생기는데, 이는 성능 오버헤드를 고려해야 하는 수준입니다. 반면 월별(monthly)로 관리하면 120개이므로 훨씬 안정적입니다.
