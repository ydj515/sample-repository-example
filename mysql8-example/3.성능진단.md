## 1. 서버 상태 및 성능 지표 모니터링

서버에서 현재 실행 중인 프로세스를 확인하고, 핵심 성능 지표인 버퍼 풀 히트율을 계산하여 서버의 전반적인 건강 상태를 진단합니다.

### 1.1. 현재 실행 중인 쿼리(프로세스) 확인
`Sleep` 상태가 아닌, 현재 활발하게 실행 중인 쿼리 목록을 실행 시간이 긴 순서대로 보여줍니다. 이 쿼리는 성능 문제를 일으키는 롱쿼리(long-running query)를 찾는 데 매우 유용합니다.

```sql
SELECT
    ID,
    USER,
    HOST,
    DB,
    COMMAND,
    TIME,
    STATE,
    LEFT(INFO, 100) as QUERY_SNIPPET
FROM information_schema.PROCESSLIST
WHERE COMMAND != 'Sleep'
ORDER BY TIME DESC;
```

  * **`ID`**: 프로세스 ID. 문제가 되는 쿼리를 강제 종료(`KILL ID;`)할 때 사용합니다.
  * **`USER`, `HOST`**: 쿼리를 실행한 사용자 및 호스트.
  * **`TIME`**: 쿼리가 현재 상태에서 머무른 시간 (초 단위). 이 값이 비정상적으로 높다면 조사가 필요합니다.
  * **`STATE`**: 스레드가 무엇을 하고 있는지 보여주는 상태 정보 (예: `Sending data`, `Creating sort index`).
  * **`QUERY_SNIPPET`**: 실행 중인 SQL 문의 앞부분 100자.

### 1.2. InnoDB 버퍼 풀 히트율(Hit Ratio) 확인

데이터 요청이 디스크가 아닌 메모리(InnoDB 버퍼 풀)에서 얼마나 처리되었는지를 나타내는 비율입니다. 이 수치가 높을수록 디스크 I/O가 적어 성능이 좋다는 의미입니다. **일반적으로 95% 이상을 목표로 합니다.**

```sql
SELECT ROUND(
   (1 - (
       (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads') /
       (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests')
       )) * 100, 2
) AS buffer_pool_hit_ratio_percent;
```

  * `Innodb_buffer_pool_read_requests`: 버퍼 풀에 요청된 총 읽기 횟수.
  * `Innodb_buffer_pool_reads`: 버퍼 풀에 데이터가 없어 디스크에서 직접 읽어온 횟수.
  * 히트율이 지속적으로 낮다면, `innodb_buffer_pool_size`를 늘리는 것이나 인덱스를 통해 성능 개선을 해야합니다.

## 2\. 테이블 및 인덱스 구조 확인

쿼리 튜닝의 기본은 대상 테이블의 구조와 인덱스 설정을 정확히 파악하는 것입니다.

### 2.1. 테이블 상태 정보 확인

테이블의 스토리지 엔진, 행(row)의 개수, 데이터와 인덱스의 크기 등 전반적인 정보를 보여줍니다.

```sql
-- 특정 데이터베이스를 사용하도록 지정
USE mysql_fundamentals;

-- 'users' 테이블의 상태 정보 확인
SHOW TABLE STATUS LIKE 'users';
```

  * **`Engine`**: 테이블의 스토리지 엔진 (예: InnoDB).
  * **`Rows`**: 테이블의 대략적인 행 개수.
  * **`Data_length`**, **`Index_length`**: 데이터와 인덱스가 차지하는 디스크 공간 (바이트 단위).

### 2.2. 테이블 생성 구문 확인

해당 테이블을 생성하는 데 사용된 `CREATE TABLE` 문 전체를 보여줍니다. 컬럼의 데이터 타입, NULL 허용 여부, 기본값, 문자셋, 제약 조건 등을 정확하게 확인할 때 유용합니다.

```sql
SHOW CREATE TABLE users;
```

### 2.3. 테이블 인덱스 정보 확인

테이블에 생성된 모든 인덱스의 상세 정보를 보여줍니다. 쿼리가 인덱스를 잘 활용할 수 있는지 판단하는 데 필수적입니다.

```sql
SHOW INDEX FROM users;
```

  * **`Key_name`**: 인덱스의 이름. `PRIMARY`는 기본 키를 의미합니다.
  * **`Column_name`**: 인덱스에 포함된 컬럼.
  * **`Cardinality`**: 인덱스에 저장된 유니크한 값의 개수 추정치. 이 값이 높을수록 인덱스의 선택도(selectivity)가 좋아 성능에 유리합니다.

## 3\. 쿼리 실행 계획 분석 (EXPLAIN)

`EXPLAIN`은 옵티마이저가 SQL 문을 어떻게 실행할 것인지 그 계획을 보여주는 가장 중요한 쿼리 튜닝 도구입니다.

### 예제 1: 인덱스를 사용하지 못하는 경우 (비효율)

`created_at` 컬럼에 인덱스가 있더라도, `YEAR()`와 같은 함수로 컬럼을 가공하면 옵티마이저가 인덱스를 사용하지 못하고 테이블 전체를 스캔(Full Table Scan)하게 됩니다.

```sql
EXPLAIN SELECT * FROM accounts WHERE YEAR(created_at) = 2023;
```

  * **예상 결과**: `EXPLAIN` 결과의 `type` 컬럼이 `ALL`(Full Table Scan)로 표시될 가능성이 높습니다. 이는 테이블이 커질수록 성능이 급격히 저하되는 원인이 됩니다.
  * **개선 방안**: `WHERE created_at >= '2023-01-01' AND created_at < '2024-01-01'` 와 같이 컬럼 자체를 가공하지 않는 방식으로 변경해야 인덱스를 활용할 수 있습니다.

### 예제 2: 인덱스를 효율적으로 사용하는 경우

`user_id` 컬럼에 인덱스가 있다면, 옵티마이저는 인덱스를 통해 원하는 데이터를 매우 빠르게 찾아냅니다.

```sql
EXPLAIN SELECT * FROM accounts WHERE user_id = 123;
```

  * **예상 결과**: `EXPLAIN` 결과의 `type` 컬럼이 `const` 또는 `ref`로 표시됩니다. 이는 매우 효율적인 접근 방식임을 의미합니다.
