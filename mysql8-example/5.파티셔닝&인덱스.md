## 1. 테이블 파티셔닝

**테이블 파티셔닝**은 거대한 테이블을 논리적으로는 하나로 유지하되, 물리적으로는 여러 개의 작은 조각(파티션)으로 나누어 저장하는 기술입니다. 이를 통해 쿼리 시 불필요한 데이터 조회를 피하고, 데이터 관리(삭제 등)를 용이하게 할 수 있습니다.

### 1.1. 파티션 상태 및 성능 분석

기존에 파티셔닝된 테이블의 상태를 확인하고 분석하는 쿼리입니다.

* **현재 파티션 상태 확인**
    각 파티션의 이름, 정의, 행 수, 데이터 및 인덱스 크기(MB)를 확인하여 전반적인 상태를 파악합니다.

    ```sql
    SELECT
        PARTITION_NAME,
        PARTITION_EXPRESSION,
        PARTITION_DESCRIPTION,
        TABLE_ROWS,
        ROUND(DATA_LENGTH / 1024 / 1024, 2) as data_size_mb,
        ROUND(INDEX_LENGTH / 1024 / 1024, 2) as index_size_mb
    FROM information_schema.partitions
    WHERE table_schema = 'financial_master_class'
      AND table_name = 'stock_trades'
      AND PARTITION_NAME IS NOT NULL
    ORDER BY PARTITION_ORDINAL_POSITION;
    ```

* **파티션별 성능 분석**
    각 파티션의 크기를 GB 단위로 보고, 행 수를 기반으로 크기 카테고리를 나누어 특히 큰 파티션을 식별합니다.

    ```sql
    SELECT
        PARTITION_NAME,
        ROUND(DATA_LENGTH / (1024 * 1024 * 1024), 2) as data_size_gb,
        TABLE_ROWS,
        CASE
            WHEN TABLE_ROWS > 50000000 THEN 'VERY_LARGE'
            WHEN TABLE_ROWS > 10000000 THEN 'LARGE'
            WHEN TABLE_ROWS > 1000000 THEN 'MEDIUM'
            ELSE 'SMALL'
            END as partition_size_category
    FROM information_schema.partitions
    WHERE table_schema = 'financial_master_class'
      AND table_name = 'stock_trades'
      AND PARTITION_NAME IS NOT NULL;
    ```

### 1.2. HASH 파티셔닝 예제

**HASH 파티셔닝**은 지정된 컬럼의 해시 값을 기반으로 데이터를 여러 파티션에 균등하게 분산시킬 때 사용합니다. 특정 값에 데이터가 몰리지 않고 고르게 분포될 때 효과적입니다.

  * **계좌별 거래 이력 테이블 (account\_id 기준 해싱)**

    ```sql
    CREATE TABLE account_trade_history (
           history_id BIGINT UNSIGNED AUTO_INCREMENT,
           account_id BIGINT UNSIGNED NOT NULL,
           -- (기타 컬럼 생략)
           PRIMARY KEY (history_id, account_id)
    ) ENGINE=InnoDB PARTITION BY HASH(account_id) PARTITIONS 16;  -- 16개 파티션으로 분산
    ```

  * **장점**

      * **데이터 균등 분산**: 데이터를 모든 파티션에 고르게 분산시켜 핫스팟(특정 파티션에 부하가 몰리는 현상)을 방지합니다.
      * **동등 비교(`=`) 쿼리에 유리**: `WHERE account_id = ?` 와 같이 특정 해시 값을 찾는 쿼리에서 파티션 프루닝(Partition Pruning)이 효율적으로 동작합니다.

  * **단점**

      * **범위 검색에 불리**: 특정 범위의 데이터를 조회할 때 모든 파티션을 스캔해야 할 수 있어 비효율적입니다.
      * **유연성 부족**: 파티션의 개수를 동적으로 변경하기 어렵습니다.

### 1.3. LIST 파티셔닝 예제

**LIST 파티셔닝**은 특정 컬럼의 값이 미리 정해진 목록 중 하나에 속할 때 사용합니다. 카테고리, 국가 코드 등 고정된 값으로 데이터를 분리할 때 유용합니다.

* **시장별 거래 데이터 (market_code 기준 리스트)**

    ```sql
    CREATE TABLE market_specific_trades (
        trade_id BIGINT UNSIGNED AUTO_INCREMENT,
        market_code VARCHAR(10) NOT NULL,
        -- (기타 컬럼 생략)
        PRIMARY KEY (trade_id, market_code)
    ) ENGINE=InnoDB
        PARTITION BY LIST COLUMNS(market_code) (
            PARTITION p_kospi VALUES IN ('KOSPI'),
            PARTITION p_kosdaq VALUES IN ('KOSDAQ'),
            PARTITION p_nasdaq VALUES IN ('NASDAQ'),
            PARTITION p_nyse VALUES IN ('NYSE'),
            PARTITION p_other VALUES IN ('OTHER', 'CRYPTO', 'FOREX')
            );
    ```
    
  * **장점**

      * **명확한 데이터 그룹화**: 데이터가 비즈니스 논리에 따라 명확하게 분리되어 관리가 용이합니다.
      * **`IN` 절 쿼리에 최적화**: `WHERE market_code IN ('KOSPI', 'NASDAQ')` 와 같은 쿼리에서 필요한 파티션만 정확히 스캔합니다.

  * **단점**

      * **새로운 값 추가의 번거로움**: 목록에 없는 새로운 값이 추가될 경우, `ALTER TABLE ... REORGANIZE PARTITION`을 통해 파티션을 재구성해야 합니다.
      * **값 목록 관리**: 파티셔닝 키 값의 목록을 사전에 모두 정의하고 관리해야 합니다.

### 1.4. RANGE 파티셔닝 예제

**RANGE 파티셔닝**은 날짜, 숫자 등 연속적인 값의 범위를 기준으로 데이터를 분할합니다. 기간별 데이터, 로그 데이터 등 시간에 따라 축적되는 데이터 관리에 가장 널리 사용됩니다.

  * **거래 로그 테이블 (거래일 기준 범위)**

    ```sql
    CREATE TABLE trade_logs (
        log_id BIGINT AUTO_INCREMENT,
        trade_date DATE NOT NULL,
        -- (기타 컬럼 생략)
        PRIMARY KEY (log_id, trade_date)
    ) ENGINE=InnoDB
    PARTITION BY RANGE (YEAR(trade_date)) (
        PARTITION p2022 VALUES LESS THAN (2023),
        PARTITION p2023 VALUES LESS THAN (2024),
        PARTITION p2024 VALUES LESS THAN (2025),
        PARTITION p2025 VALUES LESS THAN (2026),
        PARTITION p_future VALUES LESS THAN MAXVALUE
    );
    ```

      * `PARTITION p2024 VALUES LESS THAN (2025)`: `YEAR(trade_date)`의 값이 `2025`보다 작은 (즉, 2024년) 데이터가 `p2024` 파티션에 저장됩니다.
      * `PARTITION p_future VALUES LESS THAN MAXVALUE`: 정의된 범위를 벗어나는 모든 미래 데이터를 저장하는 파티션입니다.

  * **장점**

      * **시간 기반 데이터 관리에 최적**: 기간별로 데이터를 조회하거나 분석하는 쿼리 성능이 매우 뛰어납니다.
      * **손쉬운 데이터 보관 주기(Retention) 관리**: 오래된 데이터가 저장된 파티션 전체를 `DROP PARTITION` 명령어로 매우 빠르고 부하 없이 삭제할 수 있습니다.

  * **단점**

      * **데이터 쏠림 현상**: 현재 시간에 해당하는 파티션에 대부분의 쓰기 작업이 몰릴 수 있습니다.
      * **파티셔닝 키 한정**: 주로 날짜 또는 순차적으로 증가하는 숫자형 컬럼에 적용됩니다.

## 2. 고급 인덱스 전략

단순히 인덱스를 거는 것을 넘어, 인덱스의 동작 원리를 이해하고 최적의 인덱스를 설계하는 전략입니다.

### 2.1. 다중 컬럼 인덱스와 순서의 중요성

여러 컬럼을 묶어 하나의 인덱스(다중 컬럼 인덱스)로 만들 때, **컬럼의 순서**는 쿼리 성능에 결정적인 영향을 미칩니다.

* **원칙**: 선택도(Selectivity)가 높은, 즉 유니크한 값의 종류가 많은 컬럼을 앞에 두어야 합니다.
* **좋은 예**: `user_id`가 `status`보다 훨씬 유니크하므로 앞에 배치합니다.

    ```sql
    -- 좋은 예: 선택도가 높은 user_id를 앞에
    CREATE INDEX idx_orders_user_status ON orders(user_id, status, created_at);
    ```

### 2.2. 카디널리티와 인덱스 선택도

**카디널리티(Cardinality)**는 특정 컬럼에 존재하는 유니크한 값의 개수를 의미합니다. 카디널리티가 높을수록 인덱스의 **선택도(Selectivity)**가 좋아져 검색 효율이 올라갑니다.

* **카디널리티 확인 쿼리**: 전체 행 대비 유니크한 값의 비율을 계산합니다. (1에 가까울수록 좋음)

    ```sql
    SELECT
        COUNT(DISTINCT email) / COUNT(*) as email_selectivity,
        COUNT(DISTINCT status) / COUNT(*) as status_selectivity
    FROM users;
    ```

### 2.3. 접두사 인덱스 Prefix Index

`VARCHAR`나 `TEXT`처럼 긴 문자열 컬럼 전체를 인덱싱하는 것은 비효율적입니다. 이때 **문자열의 앞부분 일부만 잘라 인덱스**를 만드는 기법을 사용합니다.

```sql
-- title 컬럼의 앞 20자만으로 인덱스 생성
CREATE INDEX idx_articles_title_prefix ON articles(title(20));
```

### 2.4. `LIKE` 쿼리와 인덱스 활용

`LIKE` 검색 시 인덱스를 활용하려면 와일드카드(`%`)의 위치가 매우 중요합니다.

  * **좋은 예 (인덱스 사용 O)**: 검색어가 **앞부분부터 일치**하는 경우

    ```sql
    -- symbol 컬럼의 인덱스를 효율적으로 사용 가능
    SELECT * FROM stocks WHERE symbol LIKE 'AAPL%';
    ```

  * **나쁜 예 (인덱스 사용 X)**: 검색어가 **앞부분에 와일드카드**가 있는 경우

    ```sql
    -- 인덱스를 사용하지 못하고 Full Table Scan 수행
    SELECT * FROM stocks WHERE symbol LIKE '%APL';
    ```
