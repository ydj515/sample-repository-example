# 설계 결정 기록

이 문서는 예제를 만들면서 내린 판단과 그 근거를 남깁니다. 코드만 봐서는 "왜 이렇게 했는지" 알 수 없는 것들, 특히 **다른 선택지가 있었고 그중 하나를 고른** 지점을 다룹니다.

각 항목은 배경, 결정, 장단점, 검토한 대안 순서로 정리합니다.

---

## 1. Continuous aggregate에 realtime aggregation을 켠다

**배경**

TimescaleDB 2.13부터 신규 continuous aggregate의 기본값은 `materialized_only = true`입니다. 이 상태에서는 아직 materialize 되지 않은 최신 구간이 조회 결과에서 통째로 빠집니다. 여기에 refresh policy의 `end_offset`까지 겹치면, k6를 1분 돌리고 대시보드를 열었을 때 집계 패널이 빈 화면이 됩니다.

실제로 확인한 결과입니다.

```
최근 5분 이내 이벤트 300건 INSERT 후 조회
 raw_rows | cagg_visible
      300 |            0
```

**결정**

세 view 모두 `materialized_only = false`로 두고, daily의 `end_offset`을 1시간에서 1분으로 줄입니다.

**장점**

- 방금 들어온 이벤트도 집계 view에서 바로 보입니다. raw와 결과가 정확히 일치합니다.
- 예제의 학습 목표(raw와 집계를 비교)가 실제로 동작합니다.

**단점**

- 조회할 때마다 watermark 이후 구간을 실시간으로 계산하므로 순수 materialized 조회보다 느립니다. 구간이 좁아 실측상 차이는 미미했습니다.
- watermark 이전에 도착한 지각 데이터는 여전히 다음 갱신까지 안 보입니다(항목 3 참고).

**대안**

- **대안 A: 기본값 유지 + 애플리케이션에서 raw와 CAGG를 나눠 조회**
  - 장점: DB 설정이 단순하고, 최신 구간의 계산 비용을 앱이 통제합니다.
  - 단점: 경계 처리 로직을 직접 짜야 하고, 경계에서 중복·누락이 생기기 쉽습니다.
- **대안 B: `end_offset`을 0에 가깝게 두고 realtime은 끄기**
  - 장점: 조회는 항상 materialized라 예측 가능합니다.
  - 단점: 최신 구간을 계속 다시 굳히게 되어 갱신 비용이 커집니다. `end_offset`의 존재 이유를 없애는 선택입니다.

## 2. 일/월/년 집계를 계층형으로 쌓는다

**배경**

세 집계를 각각 raw hypertable에서 계산하면, 갱신 정책이 돌 때마다 다음을 스캔합니다.

| 뷰 | 갱신 주기 | 스캔 범위 |
|---|---|---|
| daily | 10분 | 90일치 raw |
| monthly | 1시간 | 2년치 raw |
| yearly | 1일 | 10년치 raw |

**결정**

`raw -> daily -> monthly -> yearly` 순으로 롤업합니다. raw를 읽는 것은 daily 하나뿐입니다.

평균은 저장하지 않고 `sum(duration_ms)`와 `count(*)`를 저장합니다. 상위 단계에서 `avg(average_duration_ms)`를 하면 "평균의 평균"이 되어, 호출 10건인 날과 10만 건인 날을 같은 무게로 더하게 됩니다.

**장점**

- 상위 집계의 갱신 비용이 크게 줄어, 오히려 갱신 주기를 더 짧게 가져갈 수 있습니다(1분/10분/1시간).
- 합계와 건수를 들고 있으면 어느 단계에서든 정확한 가중평균을 복원할 수 있습니다.

**단점**

- 갱신에 순서 의존성이 생깁니다. 상위 뷰는 하위 뷰의 **materialize된** 데이터를 읽으므로, 수동 갱신은 daily → monthly → yearly 순서여야 합니다.
- 최신성이 단계마다 누적됩니다. daily가 반영된 뒤에야 monthly가 따라옵니다.
- 롤업 뷰의 `GROUP BY`는 위치 참조(`GROUP BY 1, 2, ...`)로 써야 합니다. 출력 별칭 `bucket`과 원본 컬럼 `bucket`의 이름이 같아 `GROUP BY bucket`이라고 쓰면 PostgreSQL이 원본 컬럼으로 해석하고, TimescaleDB가 `must include a valid time bucket function` 오류를 냅니다.

**대안**

- **대안 A: 세 뷰 모두 raw에서 계산**
  - 장점: 뷰끼리 독립적이라 순서 의존성이 없고, 아무 뷰나 단독으로 갱신할 수 있습니다.
  - 단점: 위 표의 스캔 비용을 그대로 부담합니다. 데이터가 커지면 상위 갱신이 감당 안 됩니다.
- **대안 B: daily만 만들고 월/년은 조회 시 daily를 합산**
  - 장점: 저장 구조가 단순합니다.
  - 단점: 장기 조회에서 매번 합산 비용이 듭니다. 년 단위 조회의 이점이 사라집니다.

## 3. 백필 스크립트는 refresh 끝 경계를 열어 두지 않는다

**배경**

`refresh_continuous_aggregate(view, NULL, NULL)`처럼 끝을 열면 현재 월/년 버킷까지 materialize 되면서 watermark가 그 버킷 너머로 올라갑니다. realtime aggregation이 메꿔 줄 구간이 사라져, 백필 이후 들어오는 이벤트가 다음 정책 갱신(월 10분, 년 1시간)까지 집계에 안 잡힙니다.

실제로 백필 후 라이브 트래픽을 보냈을 때 raw 15032건, monthly/yearly 15000건으로 32건이 누락됐습니다.

**결정**

끝 경계를 `date_trunc('month', now())`로 잡아 현재 버킷을 일부러 비워 둡니다.

**장점**

- 백필 직후 라이브 트래픽을 보내도 `source=raw`와 `source=aggregate`가 즉시 일치합니다.
- refresh policy에 `end_offset`이 있는 이유와 같은 원리라, 운영 설정과 일관됩니다.

**단점**

- 현재 버킷은 materialize 되지 않아 조회할 때마다 실시간 계산합니다.
- 이 규칙을 모르고 수동으로 전체 갱신하면 같은 문제가 재현됩니다. 그래서 스크립트와 README에 이유를 남겼습니다.

## 4. 백필 스크립트는 정책 job을 끄지 않는다

**배경**

처음에는 `alter_job(scheduled => false)`로 압축·보존·갱신 job을 멈췄다가 끝에서 되살리는 구조였습니다. 대량 INSERT 중에 정책이 끼어드는 것을 막으려는 의도였습니다.

문제는 실패 경로입니다. 스크립트는 `ON_ERROR_STOP on` 상태라 중간에 실패하면 그 자리에서 멈추고, **job이 꺼진 채로 남습니다.** 압축·보존·집계 갱신이 조용히 멈추고 사용자는 알 방법이 없습니다. psql에는 `finally`가 없어 복원을 보장할 수단도 없습니다.

**결정**

job을 끄지 않습니다.

**장점**

- 조용히 망가지는 실패 모드가 사라집니다.
- 스크립트가 단순해집니다.

**단점**

- 백필 도중 정책이 실행될 수 있습니다. 다만 실질적 문제가 없다고 판단했습니다.
  - INSERT는 단일 문장이라 원자적이고, 정책이 중간 상태를 보지 않습니다.
  - 압축은 `if_not_compressed => true`라 정책이 먼저 압축했어도 문제없습니다.
  - refresh는 TimescaleDB가 뷰 단위로 직렬화합니다.

**대안**

- **대안 A: job을 끄되 복구 명령을 안내**
  - 장점: 백필 중 간섭이 확실히 없습니다.
  - 단점: 사용자가 안내문을 놓치면 그대로 방치됩니다. 실패 시 손상이 조용하다는 성질이 그대로입니다.
- **대안 B: 백필을 애플리케이션 코드로 옮기고 try/finally로 복원**
  - 장점: 복원을 보장할 수 있습니다.
  - 단점: SQL 한 파일로 끝나던 것이 코드·빌드·실행 경로를 요구하게 됩니다. 예제의 접근성이 떨어집니다.

> 남은 상호작용이 하나 있습니다. 기본 백필 구간(400일)이 보존 기간(180일)보다 길어, 보존 job이 실행되면 오래된 raw가 삭제됩니다. 집계는 남으므로 "원본은 버려도 통계는 남는다"를 보여 주는 구성이지만, 그 구간에서는 raw와 aggregate 결과가 달라집니다. 스크립트가 실행 결과에 이 사실을 경고로 출력합니다.

## 5. 인증 스냅샷과 matcher를 한 객체로 묶어 교체한다

**배경**

`ApiAccessService`는 API Key 스냅샷과 라우트 matcher를 캐싱합니다. 처음에는 두 개의 `@Volatile` 필드에 순서대로 썼습니다. 기동 시 1회만 갱신할 때는 문제가 없었지만, 주기 갱신(60초)을 추가하면서 요청 스레드와 동시에 실행됩니다.

새 snapshot을 쓴 직후 matcher를 쓰기 전에 요청이 끼어들면, **옛 matcher가 찾아 준 `route.id`를 새 snapshot의 권한 맵과 대조**하게 됩니다.

**결정**

두 값을 `AccessState` 하나로 묶어 volatile 쓰기 한 번으로 교체합니다. 요청 경로에서는 한 번만 읽어 지역 변수에 담습니다.

**장점**

- 중간 상태가 노출되지 않습니다. 두 값이 항상 같은 세대입니다.
- 락이 없어 요청 경로에 경합이 생기지 않습니다.

**단점**

- 갱신 때마다 matcher를 새로 만들어 정규식을 다시 컴파일합니다. 라우트 수가 적어 무시할 수준입니다.
- 갱신 직전에 시작한 요청은 옛 세대로 끝납니다. 인증 캐시 성격상 허용 가능한 지연입니다.

**대안**

- **대안 A: `synchronized` 또는 `ReadWriteLock`**
  - 장점: 직관적입니다.
  - 단점: 읽기가 압도적으로 많은 경로에 락을 넣게 됩니다. 불변 객체 교체로 해결되는 문제입니다.
- **대안 B: matcher를 캐싱하지 않고 요청마다 생성**
  - 장점: 상태가 없어 경합 자체가 없습니다.
  - 단점: 요청마다 정규식 컴파일과 정렬 비용을 치릅니다.

## 6. 통계 응답에 전체 행 수 상한을 둔다

**배경**

`limit`을 "버킷별 상위 N"으로 바꾸면서 전체 행 수 상한이 사라졌습니다. `period=day`로 넓은 구간을 `limit=500`으로 조회하면 이론상 수만 행이 한 응답에 담깁니다. 실측으로 61버킷 조회 시 최대 30,500행까지 가능했습니다.

DB 용량 문제가 아니라 직렬화 메모리, 전송량, 클라이언트 렌더링이 먼저 무너집니다.

**결정**

`ApiStatsReader.MAX_TOTAL_ROWS = 5000`을 바깥 `LIMIT`으로 적용하고, 상한에 걸리면 `X-Result-Truncated: true` 헤더를 붙입니다.

**장점**

- 응답 크기에 확정적인 상한이 생깁니다.
- 응답 스키마(JSON 배열)를 바꾸지 않아 기존 클라이언트가 깨지지 않습니다.
- 잘림을 조용히 넘기지 않습니다. 클라이언트가 헤더로 감지할 수 있습니다.

**단점**

- 잘린 뒤의 데이터를 이어서 받을 방법이 없습니다. 구간을 좁혀 다시 요청해야 합니다.
- 헤더는 본문보다 놓치기 쉽습니다.

**대안**

- **대안 A: 조회 구간 길이를 입력 단계에서 제한**
  - 장점: 원인을 입구에서 막아 예측 가능합니다. 잘림 자체가 없습니다.
  - 단점: 최악의 경우를 기준으로 막게 되어, 실제로는 작은 결과가 나올 정당한 요청까지 거부합니다.
- **대안 B: 커서 기반 페이지네이션**
  - 장점: 상한 없이 전체를 안전하게 순회할 수 있습니다.
  - 단점: 응답 스키마가 바뀌고 커서 상태 관리가 필요합니다. 예제 규모에 비해 과합니다.
- **대안 C: 응답을 `{ items, truncated }` 객체로 감싸기**
  - 장점: 잘림 정보가 본문에 있어 놓치기 어렵습니다.
  - 단점: 기존 배열 응답을 쓰는 클라이언트가 모두 깨집니다.

## 7. 예외 처리는 프레임워크가 정한 4xx를 건드리지 않는다

**배경**

`error_type` 컬럼을 채우려고 `@RestControllerAdvice`에 `@ExceptionHandler(Exception::class)`를 두었더니, Spring MVC가 자체적으로 4xx로 매핑하던 예외까지 전부 가로채 500으로 바꿨습니다.

```
GET  /api/products/abc  (타입 불일치)   500  <- 400이어야 함
POST /api/products      (미지원 메서드) 500  <- 405여야 함
GET  /api/nope          (없는 경로)     500  <- 404여야 함
```

상태 코드만의 문제가 아닙니다. 클라이언트 실수가 서버 오류로 집계되어 `error_type`에 프레임워크 예외명이 쌓이고 `failure_rate`가 부풀었습니다. **이 예제가 측정하려는 지표 자체가 오염됐습니다.**

**결정**

`ResponseEntityExceptionHandler`를 상속해 프레임워크 예외는 부모가 표준 상태 코드로 처리하게 두고, `handleExceptionInternal`을 오버라이드해 5xx일 때만 `error_type`을 남깁니다. 예외 메시지는 응답에 담지 않고 로그로만 남깁니다.

**장점**

- 상태 코드가 HTTP 의미에 맞습니다.
- 통계가 서버 오류와 클라이언트 실수를 구분합니다.
- Spring Boot 기본값(`server.error.include-message=never`)이 지키던 보호를 되돌립니다. 이전에는 `"No static resource ..."`나 JSON 파서 내부 메시지가 그대로 노출됐습니다.

**단점**

- `ResponseEntityExceptionHandler`가 처리하는 예외 목록에 의존합니다. Spring 버전이 올라가면 목록이 바뀔 수 있습니다.
- 프레임워크 4xx 응답은 RFC 7807 `ProblemDetail` 형식이고, 우리가 던지는 오류는 `{status, message}` 형식이라 응답 형태가 두 가지입니다.

**대안**

- **대안 A: 잡을 예외를 하나씩 명시**
  - 장점: 동작이 명시적이라 읽기 쉽습니다.
  - 단점: 새 예외 유형이 생길 때마다 빠뜨리기 쉽습니다. 빠뜨리면 다시 500이 됩니다.
- **대안 B: 예외 처리를 두지 않고 `error_type` 수집을 포기**
  - 장점: 프레임워크 기본 동작을 그대로 씁니다.
  - 단점: `error_type` 컬럼이 계속 비어 있고, `/api/unstable` 같은 예제 시나리오가 의미를 잃습니다.

> 이 문제는 컨트롤러 메서드를 직접 호출하는 단위 테스트로는 잡히지 않습니다. 디스패처를 거치지 않기 때문입니다. `ApiExceptionHandlerTest`가 MockMvc로 검증합니다.

| `/api/stats/*` 인증 | 없음(캡처 필터 제외 대상이라 인증도 함께 제외) | 별도 관리자 인증 |
| 미등록 경로 | default-allow. `api_routes`에 없으면 API Key 없이 통과 | default-deny |
| `client_ip` / `user_agent` | 원본 저장 | 마스킹 또는 짧은 보존 기간 |
| 데모 API Key | README와 seed에 평문(저장은 SHA-256 해시) | 발급·회수 절차 |
| CAGG 보존 정책 | 없음(무한 증가) | 카디널리티에 따라 필요 |

CAGG 보존 정책을 두지 않은 이유는 증가 속도가 매우 느리기 때문입니다. 행 수는 `버킷 수 × 고유 조합 수`로 정해지고, 예제는 클라이언트 10 × 라우트 6 = 최대 60개입니다. 실측으로 raw 80만 건이 daily 24,000행, monthly 840행, yearly 120행으로 줄었습니다.

> 위험한 경우는 `path_pattern`의 카디널리티가 폭발할 때입니다. `path_pattern`에 원본 `path`(예: `/api/products/12345`)가 들어가면 조합 수가 사실상 무한이 되고 집계가 raw만큼 커집니다. `path`와 `path_pattern`을 분리해 저장하는 이유가 여기 있습니다.
